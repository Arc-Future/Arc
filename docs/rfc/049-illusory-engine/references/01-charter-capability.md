## 1. 动机

`std` 需要一套**虚拟现实优先**的游戏引擎，为「可动元素」提供统一的组织与驱动模型。这里「可动元素」包括人物、怪物、门、拾取物、环境交互物等一切**受时间与行为驱动**的对象。引擎要解决工业界的三个常态痛点，并因此确立三条主线：

| 痛点                   | 后果               | 引擎主线                            |
| -------------------- | ---------------- | ------------------------------- |
| 对象模型混乱（每条行为挂在哪、依赖怎样） | 代码纠缠、难拆难测、多人协作冲突 | **对象模型**：Actor 壳 + Component 挂点 |
| 行为写在渲染/逻辑回调里，时序不可控   | 步进不可预测、帧率抖动、无回放  | **行为模型**：async 行为 + 固定步长驱动      |
| 渲染、逻辑、物理共享同一时间源却不一致  | 穿模、抖动、网络不同步      | **确定性步进**：SimulationTick 唯一时间源  |

三条主线分别对应本文档链 [03 对象模型](03-object-model.md)、[05 行为模型](05-behavior-model.md)、[04 仿真核心](04-simulation-core.md)。

## 2. 对象模型与行为模型选型

引擎只做两个最关键的选型裁决，其余皆从这两个裁决派生。判据唯一：**业界最好用、最易上手**，同时不牺牲确定性。

### 2.1 对象模型：Actor + Component（不取 ECS）

对比三条业界路径，取 Actor + Component：

| 方案                    | 代表                    | 上手       | 代价              | 裁决 |
| --------------------- | --------------------- | -------- | --------------- | -- |
| 继承式（class 深继承）        | 早期 Unity/Godot        | 直观       | 多继承冲突、行为纠缠、组合死区 | ✗  |
| ECS（纯数据+系统）           | Unity DOTS、Bevy       | 性能优      | 思维陡、样板多、小项目过重   | ✗  |
| **Actor + Component** | Unity 现代、Unreal Actor | 组合优先、易上手 | 需纪律约束           | ✓  |

裁决结论：

- **Actor 是壳**，持有身份（`ActorId`）、空间（`Transform`）、标签（`GameplayTags`）与组件仓库，**不装行为**。差异化一律靠挂组件，禁止深派生子类。

- **Component 是挂点**，承载数据与能力。M1/M2 为数据标桩，行为驱动论证见 [05](05-behavior-model.md)。

- **不引入 ECS**：太小规模无需架构债；确定性不靠 ECS 保证，而由固定步长与单一时间源保证（[04](04-simulation-core.md)）。

- **不引入事件系统**：跨对象通信用 `Signal`/委托，符合 Arc 去除事件机制的既定原则。

### 2.2 行为模型：async 行为 + BehaviorRunner（不取裸协程）

对比 Unity 协程、Godot await、GAS 生命周期，取 **async 方法 + 固定步长驱动的 BehaviorRunner**：

| 方案                            | 代表       | 上手      | 确定性                 | 裁决    |
| ----------------------------- | -------- | ------- | ------------------- | ----- |
| 协程（yield API 写流程）             | Unity 协程 | 直观      | 弱（随帧/随秒）            | △ 取其形 |
| await 原生异步                    | Godot、C# | 更直观     | 依赖调度器               | △ 取其用 |
| **async 行为 + BehaviorRunner** | 融合       | 同 async | 强（按 SimulationTick） | ✓     |

裁决结论：

- 开发者以 `async` 方法书写行为流程，用 `await ctx.WaitTick()` 等待，天然可读、可组合、可取消。

- 底层由 `BehaviorRunner` 按 `SimulationTick` 驱动，让 async 行为的推进**绑定到确定性步印**而非帧率或墙钟，从而可记录、可回放、可网络预测（[07](07-vr-networking-directions.md)）。

- 异步能力直接复用 Arc 既有的 `Task`/`CancellationToken`/`Async` 契约（RFC 009），**零新机制**。

完整契约见 [05 行为模型](05-behavior-model.md)。

## 3. 能力域分层

引擎能力按与核心仿真/对象模型的耦合度分四层，从复用走向自建：

| 层            | 能力                  | 来源           | 例                                                                   |
| ------------ | ------------------- | ------------ | ------------------------------------------------------------------- |
| **L0 基础**    | 语言、集合、异步、数学、DI      | 复用 std       | `List<T>`/`Dictionary`、`Task`、`Math`、`Arc.DI`                       |
| **L1 仿真内核**  | 固定步长、世界组织、对象模型、行为驱动 | 引擎自建（本文档链核心） | `IWorld`、`SimulationTick`、`BehaviorRunner`                          |
| **L2 表现与驱动** | 渲染、UI、2D 骨骼动画、音频、输入 | 自建+渲染托底 | 2D 骨骼动画（[06](06-skeletal-animation.md)）；渲染托底 `Arc.UI` |
| **L3 外围与生存** | 物理、导航、网络、持久化        | DI 注入/方向预留   | 物理/导航注入（[01](#7-能力缺口登记)）；网络预留（[07](07-vr-networking-directions.md)） |

分层纪律：**L1 自建、不混领域翻译**；L3 领域能力走 DI 注入，引擎核心不内嵌物理/网络求解器。渲染不在 L1——引擎表现一律托底既有 `Arc.UI` wgpu 面，不新造渲染后端（RFC 037）。

## 4. 复用 × 自建

| 能力    | 复用 std 的                                       | 引擎自建                            |
| ----- | ---------------------------------------------- | ------------------------------- |
| 异步/取消 | `Task`、`CancellationToken`（RFC 009）            | BehaviorRunner 的步进式调度封装         |
| 数学/向量 | `Math`→LLVM intrinsic、`Transform`（Arc.Math）    | 无                               |
| 依赖注入  | `Arc.DI` 编译期工厂（RFC 023）                        | 引擎服务宿主（`WorldOptions.Services`） |
| 渲染    | `Arc.UI`/wgpu `WgpuRender`/`DrawList`（RFC 037） | 组合、绘制批的引擎侧编排（L2）                |
| 数据容器  | `List`/`Dictionary`/`HashSet`（RFC 007/021）     | 组件仓库、ActorRegistry 的检索语义        |
| 网络/物理 | 无                                              | 不内置，DI 注入（L3）                   |

## 5. 架构纪律

- **internal 编排**：核心编排类（`World`、`Simulation`、`ActorRegistry`、`BehaviorRunner` 等）一律 `internal`，开发者仅经 `IWorld` 等门面交互。此纪律沿用 RFC 020 internal 边界。

- **引擎核心不内嵌领域能力**：物理、网络、SQL 等任何领域翻译逻辑不得进仿真内核；一律经 DI 注入或数据驱动。

- **不硬编码游戏数据**：预制体、动画 Clip、能力模板、标签语义一律数据驱动，禁止把需持续维护的数据写死在代码里。

- **确定性优先**：一切时间决策引用 `SimulationTick`，不读墙钟（[04](04-simulation-core.md)）。

- **单一惯用法**：每语义只保留一种写法，禁止双轨（例如行为只走 async behavior，不并存裸协程 API）。

- **命名与接口**：全引擎强制遵守 [02 命名与接口规范](02-api-conventions.md)。

## 6. 文档架构纪律

本文档链采用**渐进式披露**：主章程（RFC 049）定身份、裁边界、指路；深度契约按主题下沉至本 references/。规则：

- **编号顺序即阅读顺序，也是合规实现顺序**；每篇只依赖前篇编号，链路单向，无网状回环。

- **禁止补丁式加文档**：原生能力/方向新增，先在此能力缺口登记（§7）与 [07 方向预留](07-vr-networking-directions.md) 登记，再固化细案；不临时在后置文档追加成碎片。

- **不留过时/重复**：文档被改写时整篇重排，删除与被覆盖内容，保证整体顺序自洽。
