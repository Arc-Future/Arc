## 高风险重定义

Agent 是员工，不是要防的威胁。"高风险"不是"会搞坏电脑"，而是**高沟通价值的决策点**——员工在关键决策点主动找老板对齐，其余放手干。

**防御模型 → 协作模型**：

| 旧范式 | 新范式 |
|--------|--------|
| 防止 agent 搞破坏 | 确保 agent 在关键决策点对齐 |
| 安全名单 | 协作确认清单 |
| 每步问人（卡死） | 机器自判能否决策 → 不能时升级人 |

## 协作确认点清单

计划门闩批准后，执行环在以下点触发人确认：

### 必须确认（D7 人验收门必经）

| 触发条件 | 确认问题 | 谁确认 |
|----------|----------|--------|
| 改 public API / ABI / std | "确定要这么改吗？影响面 X 个包" | 开发者 |
| 删除/重构核心模块 | "意图确认：这个模块的职责你计划怎么迁移？" | 开发者 |
| 需求与设计冲突 | "方向确认：当前设计覆盖不了需求，请补充方向" | 开发者 |
| 验收标准模糊 | "你要什么结果？验收标准需要足够具体才能执行验证" | 开发者 |
| 设计评审标记项 | 远见/收敛/设计模式合理性等机器判不了的问题 | 开发者 |

### 自动确认（机器可判，不需人）

| 触发条件 | 动作 |
|----------|------|
| 改非 public 实现 | 无需人确认 |
| 新增文件（非核心） | 无需人确认 |
| 修复编译/测试失败 | 自动迭代，≤3 轮 |
| 绿点快照推进 | 自动推进 |
| 反模式可查项命中 | 自动修复或标记 |

### 异常升级

| 场景 | 动作 |
|------|------|
| 迭代超限（3 轮不绿） | 回滚绿点 + 升级人（"修复失败，请确认方向或回退"） |
| 验证环境不可用 | 升级人（"环境不可用，请确认验证方式"） |
| 语义意图冲突 | 升级人（"测试全绿但行为可能不符意图，请确认"） |

## 机器收敛点（并行协作 · B6）

> 并行开发（多会话 / 多切片 / 多 std 改名 / 多领域并进）在**合并 / 提交前**设显式机器收敛点，状态可机器断言；未收敛不宣称完成（来源 [harness-llm-lessons B6](harness-llm-lessons.md)）。

并行改动落地前，必须通过下列**机器收敛点**（每项可执行命令断言，禁凭记忆）：

| 收敛点 | 可执行断言 | 未通过时 |
|--------|-----------|---------|
| **统一 build** | `cargo build -p arc` exit=0；端到端 `cargo run -p arc -- build <proj>` 绿 | 修复或改回，不得带着红 build 合并 |
| **统一 test** | `cargo test --workspace`；相关 e2e（`cargo test -p arc-integration --test <e2e>`）不回归 | 定位并修复，禁以「并行他人改动导致」为由跳过 |
| **统一落盘** | `git status --porcelain` 改动集对齐；状态登记（plan.md / RFC references 状态表）与代码同步刷新 | 状态登记滞后视为未收敛，禁宣称完成 |
| **命名轴单一化** | `rg` 全库零残留双轨命名（如 `_digitValue` / `DigitValue` 同义并存） | 单一化后再合并，禁双轨 |

**纪律**：并行改动各自独立验收后，在收敛点**串行统一** build/test + 落盘；收敛点通过才可宣称完成 / 合入。收敛点本身走标准 HITL / 机器断言，不另起通道。

## 确认交互模式

所有确认点走 HITL 门闩（038 §5），不另起通道：

```as
// Harness 框架：确认点走标准 HITL 协议
// 确认点 = 带确认原因的 AIHumanRequest
// 确认结果 → 记录进事件日志（决策轨迹）
```

## 零防御

禁止以下防御性设计：
- 沙箱"不允许写系统文件"（规范员工靠协作确认，不靠防火墙）
- 文件操作前处处问人（只有设计/计划/验收相关的高价值决策点才问）
- 信任评分 / 限速 / 能力单日配额（Agent 是员工，不是 API 调用者）
