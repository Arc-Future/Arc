# 测试先行与纠偏同步

> 关联 [043 Coding Agent Harness 工程(../../043-harness.md) §9。本子项定义验收测试先行锁定的流程，以及纠偏时测试随 **AIRfc** 升版同步的协议。宣称门闩见 [llm-gates](llm-gates.md)；完成判定见 [DoD](definition-of-done.md)。

## §0 宣称门闩

| # | 门闩 |
|---|------|
| 1 | 验收面属 **AIRfc Acceptance**；未锁定验收测 → 禁止进入实现宣称 |
| 2 | 纠偏 = AIRfc Revision+1，测试必须同步；禁「旧测全绿」冒充新方向完成 |
| 3 | 实现阶段禁擅自改已批准测试；改测未经升版/评审 → 禁止宣称 D3 通过 |

## 核心原则

测试是意图的**可执行表达**，不是"验证的附属品"。测试先行解决两个核心问题：
1. **你要什么结果？**——验收测试把模糊需求具象化，Harness 自己能不能完成，测试一跑就知道。
2. **验证信号可信吗？**——测试独立于实现，避免"模型写实现、同时写/改测试"的自我欺骗风险。

## 测试先行流程

### 锁定阶段（AIRfc 确立后、实现前）

```
意图 → 验收场景 → 验收测试 + 断言 → 实现 → 测试通过
```

| 步骤 | 产出 | 确认 |
|------|------|------|
| 1. 意图澄清 | 用户一句话 → 可感知结果 | 开发者确认 |
| 2. 验收场景 | 每个场景描述"输入 → 预期行为 → 可观察结果" | 开发者确认 |
| 3. 验收测试 | 场景对应可执行测试（含断言，独立于实现） | 自动验证（测试能编译 + 初始失败符合预期） |
| 4. 实现 | 让测试通过 | 自动迭代 |
| 5. 验证全绿 | 测试全部通过 | 进入 D3 |

### 纠偏同步

纠偏只升版 AIRfc，测试随验收面同步更新：

```text
用户补充方向 → AIRfc Revision+1
  → 验收场景同步更新
    → 验收测试同步更新
      → 旧测试标记为"过时"（保留在事件日志决策轨迹）
        → 执行环重对齐最新测试
```

**测试永远对应最新方向**，验证信号永远可信。不会出现"旧测试全绿、新方向不对"的假象。

## 自证风险防御

| 风险 | 防御 |
|------|------|
| 模型写实现、同改测试（自我欺骗） | 测试先行锁定：测试在实现前由开发者确认，实现不得修改已批准的测试 |
| 纠偏时测试未同步 | 纠偏协议强制测试同步更新（AIRfc Revision+1 → 测试版本+1） |
| 测试覆盖不全 | 验收场景覆盖需求边界，D5 自审门要求每条 acceptance 有可执行证明 |
| 测试本身写错 | 开发者确认验收场景 → 测试基于场景，不是模型自编。测试能编译 + 初始失败符合预期 |

## 纠偏同步的测试治理

| 事件 | 测试动作 |
|------|----------|
| 需求补充 | 添加新测试；旧测试不变（补充覆盖） |
| 需求变更 | 修改对应测试，旧测试移入"过时"集（保留在决策轨迹） |
| 需求撤销 | 对应测试标记为"已撤销"（保留在决策轨迹） |
| 设计变更（需求不变） | 测试不变（接口不变不涉及测试）；接口变 → 测试同步更新 |
