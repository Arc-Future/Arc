# Harness 工程自审方法论（用 Harness 方法论审 Harness 自身）

> 关联 [043 Coding Agent Harness 工程(../../043-harness.md)（§2 宣称纪律）· [设计先行与设计评审](design-review.md) · [可执行 DoD](definition-of-done.md) · [纠偏协议](anchor-correction-protocol.md) · [回合小结](work-summary.md) · [LLM 门闩](llm-gates.md)。本子项定义 **Harness 工程自审方法论**：以「Arc.Agent.Harness 体系建设」为样本，用 Harness 自己的规则对体系自身做系统性方法学检视与纠偏。它沉淀的是**一审法 + 评判标准 + 纠偏纪律**，不承载任何一次具体评审的实现状态或验收记录。

## §0 自审自身的宣称门闩

| # | 门闩 |
|---|------|
| 1 | 每部分有「结论 + 证据 + 偏差」三段式，证据为具体 `文件:行` / commit，非泛泛而谈 |
| 2 | 诚实暴露偏差与缺陷，禁止歌功颂德 |
| 3 | 只读研究：不改 `.as` 业务代码、不 git commit/push；自审报告自身不得宣称「体系已完成/终态」 |
| 4 | 无法现场复验项显式标注「未复验」，不得冒充已验 |
| 5 | 不得将未提交改动误判为已提交基线状态 |

> 未过门闩就下结论，结论仅作回顾用途，不构成对体系「Completed / 终态」的宣称；体系完成度以 043 宣称纪律与 DoD 为准。

## §1 自审的意图与方法

**意图**：验证「Arc.Agent.Harness 体系建设」是否忠实服务 RFC 043 的最初意图（面向 Arc 开发者用户的编码智能体领域工程，方向环确立目标、执行环实现验证，高质量来自方向确认 + 验证闭环）。

**方法**：以 Harness 自己的规则为镜子（AIRfc 立项 / 意图·设计·验收三面、双环、D0–D7、纠偏协议、回合小结、宣称纪律），对体系建设逐项对照检视。**自审样本本身不要求走 Harness 全流程**——这是「用方法论照镜子」的法，而非对样本的额外流程要求；但样本若声称按 Harness 流程交付，其走没走流程本身即是待查项（避免「建设自己不用自己方法论」的自指缺口）。

## §2 评判维度（对照 design-review 清单）

| 维度 | 评判要点 |
|------|---------|
| 有远见 | 设计文档是否含风险/成本/非目标；缺陷是否带探针 + 根因 + 状态；回滚是否为真实回滚而非只发事件 |
| 懂收敛 | 是否删除无用的试探类型/平行实现；是否有防假绿语义（如 `Pending≠Passed`） |
| 模块化 | 单文件单职责；分层依赖单向；基座不写死领域逻辑 |
| 零冗余 | 是否存在为不存在需求做的前置扩展；反模式门是否做源码级扫描 |
| 合理用设计模式 | 策略/依赖注入是否走正道；是否用布尔参数覆盖人类门判定等薄壳手写协议替代真正机制 |

## §3 缺陷 / 偏差的分类学（审什么）

按类别逐面检视，给出严重度（🟢 轻度 / 🟡 中度 / 🔴 高风险）：

| 类别 | 检视内容 |
|------|---------|
| 意图/实现 | 规格 vs 实现是否有信号降级；文档是否把「目标态」写成「现状」 |
| 设计 | 身份是否模糊（试探壳是否被当终态门面）；依赖是否漂移；稳定标识是否可作跨会话键 |
| 收敛 | 是否存在无消费者的前置扩展；复杂度过高是否高于最低可证伪需要 |
| 验收 | 每条 acceptance 是否有可执行证明；证据块是否只覆盖部分里程碑 |
| 纠偏 | 规避注释是否随根因修复过期；是否独立登记为缺陷条目 |
| 宣称 | 是否把试探当终态 / Pending 当 Passed / 无证据声称完成；登记是否滞后过时 |
| 文档 | 链接是否断链；旧型号/路径是否残留 |
| 协作/过程 | 编译器核心结构性修复口径是否一致；提交颗粒度是否可审计 |

## §4 假完成信号排查清单

| 信号 | 判别标准 |
|------|---------|
| 试探类型当终态 | 相关类型是否已删除；文档是否明确「试探≠终态」 |
| Pending 当 Passed | 聚合判定是否任一非 Passed 即 false（fail-closed） |
| 声称完成但无证据 | 每条完成是否有验收证据块 |
| 调用方假确认人类门 | API 是否允许程序化把 `NeedsHuman` 门替换为 `Passed`；文档是否只禁模型路径假绿而未禁调用方假确认 |

## §5 纠偏纪律

- **增量升版、非推翻**：不推倒现有建设，按优先级实施，每项附验收信号。
- **纠偏与代码/文档同变更集落地**：命名收敛、枚举化、缺陷规避等均以文档 + 代码同批提交并登记。
- **方向性纠偏落版本演化**：方向变更（如分层归属调整、类型替换）体现在 RFC / references 的版本演化中，有据可查。
- **基础面冻结纪律**：编译器核心结构性修复即使自称「无语义变化」，触及稳定面时仍应留 RFC/提交确认记录，避免静默改动影响面大的东西。
- **提交纪律**：避免跨领域大 commit；历史 WIP commit 不得滞留 main；杜绝将临文件（如 crash 日志）提交进仓库。
- **登记优先于硬改**：对真实写法但因编译器缺陷 build 红者，按「登记而非硬改 std」挂账；编译器缺陷须有复现探针 + 根因 + 状态。

## §6 诚实边界（自审方法的适用范围）

- 本方法论审的是「体系自身建设」的方法学与宣称纪律，**不新增、不替代**能力子项的设计契约（能力面以 airfc / definition-of-done / conflict-fabric 等为准）。
- 「人确认」痕迹无法仅凭仓库强证（commit 含协作署名）：凡依赖人对关键决策的确认者，须以文档/提交记录为据，无法现场复验则标注「未复验」。
- 自审结论只反映检视时点下的方法学判定；任何「未实现 / 未宣称」的边界须诚实留档。
